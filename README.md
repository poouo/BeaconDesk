# BeaconDesk

BeaconDesk is an open-source remote assistance project inspired by tools such as AnyDesk and Sunlogin. It is designed for legal, transparent, user-authorized support workflows.

The project explicitly does not implement hidden operation, silent control, permission bypassing, antivirus evasion, credential theft, or privacy-invasive behavior.

## Current MVP

- Go connection server over TCP JSON Lines or WebSocket.
- Modern self-drawn Go Windows client UI built with Gio.
- Headless client mode for smoke testing.
- Device identity generation.
- Token-protected device registration.
- Optional 6-digit temporary verification codes for session requests.
- Heartbeat ping/pong with RTT display.
- Server-side heartbeat timeout cleanup and reconnect-aware clients.
- Basic session request/confirm/ready signaling.
- Simulated frame forwarding through the server.
- Optional Windows GDI screen capture with JPEG frame forwarding.
- Sender-side static-screen detection, unchanged-frame throttling, bitrate display, packet-loss estimate, telemetry forwarding, and JPEG quality backoff.
- Sender-side dynamic FPS backoff/recovery using bitrate, RTT, and packet-loss signals.
- Server-side token-bucket bandwidth limiting for forwarded payloads.
- GUI-side incoming request approval before a session is accepted.
- Trusted device remember/revoke UI for explicit local authorization reuse.
- Server-enforced session mode and remote-input permission checks.
- Controller-side request mode selection for view-only or view-and-control sessions.
- Local audit log for incoming requests, approvals, session readiness, and remote input events.
- Optional remote mouse and keyboard input after explicit input permission.
- BeaconDesk icon assets for Windows executables.
- Native TLS listener support for encrypted client-server communication.
- Windows client update check against GitHub Releases.
- Server-hosted browser control page from controlled-side temporary links.
- Windows client web-control link management with expiry display, copy/open, refresh, and revoke.
- Release checksum generation and checksum verification in the Linux installer.

The MVP transport can run as plain TCP for simple local testing. Production deployments should use the native TLS listener or put TLS in front of the connection server. The Windows client defaults to WebSocket + TLS; disabling TLS is intended only for local testing.

## Run the MVP

Start the connection server:

```bash
go run ./cmd/relay-server -config configs/relay.example.conf
```

`configs/relay.example.conf` is a developer-friendly local example and leaves plaintext enabled for quick testing. The one-line Linux installer creates a TLS-enabled WebSocket configuration by default. For any public server, use TLS and set `allow_insecure_plaintext = false`.

For native TLS, configure certificate paths in the server config:

```text
listen = ":8443"
shared_token = "change-me"
tls_cert_file = "/etc/beacondesk/tls/fullchain.pem"
tls_key_file = "/etc/beacondesk/tls/privkey.pem"
allow_insecure_plaintext = false
```

For WebSocket server mode, set:

```text
transport = "websocket"
websocket_path = "/ws"
```

Web control links are served by the connection server. In TCP transport mode, use a separate HTTP listener:

```text
web_control_enabled = true
web_control_path = "/web"
web_listen = ":8080"
public_base_url = "https://relay.example.com"
```

In WebSocket transport mode, the server serves `/web` from the same HTTP listener as `/ws`. A web-control link is generated by the controlled Windows client and targets that device only. Opening the link starts a browser-side request, but the controlled user must still approve the session in BeaconDesk before video or input is routed.

Start a controlled peer:

```bash
go run ./cmd/client-windows -headless -server 127.0.0.1:8443 -name controlled -role controlled -auto-accept -mock-frames -token change-me
```

To require a temporary code before the server forwards requests to this peer:

```bash
go run ./cmd/client-windows -headless -server 127.0.0.1:8443 -name controlled -role controlled -publish-code -mock-frames -token change-me
```

The code is valid for 10 minutes, is kept only in server memory, and is consumed after one successful request.

`-auto-accept` is only intended for local MVP testing. The native Windows GUI shows incoming requests and requires the controlled-side user to allow or reject them.
Remote input is disabled unless the controlled side enables `Allow remote input` in the GUI or starts headless mode with `-enable-input`.

To send real screen preview frames from the controlled peer, explicitly enable screen capture:

```bash
go run ./cmd/client-windows -headless -server 127.0.0.1:8443 -name controlled -role controlled -auto-accept -screen-frames -capture-fps 2 -capture-width 1280 -capture-height 720 -capture-quality 55 -token change-me
```

Low-bandwidth sender options:

```bash
go run ./cmd/client-windows -headless -server 127.0.0.1:8443 -name controlled -role controlled -screen-frames -capture-fps 2 -bandwidth-limit-kbps 1024 -static-frame-seconds 8 -token change-me
```

Copy the printed controlled device ID, then start a controller:

```bash
go run ./cmd/client-windows -headless -server 127.0.0.1:8443 -name controller -role controller -target dev_xxx -token change-me
```

If the target published a temporary code, include it:

```bash
go run ./cmd/client-windows -headless -server 127.0.0.1:8443 -name controller -role controller -target dev_xxx -target-code 123456 -token change-me
```

The controller should receive simulated frame events after the session is ready.

Connect to a TLS server:

```bash
go run ./cmd/client-windows -headless -server relay.example.com:8443 -tls -tls-server-name relay.example.com -token change-me
```

Connect to a WebSocket server:

```bash
go run ./cmd/client-windows -headless -server relay.example.com:8443 -transport websocket -ws-path /ws -tls -tls-server-name relay.example.com -token change-me
```

`-tls-skip-verify` exists only for local self-signed certificate testing.

## Windows Native Client

The client uses a modern self-drawn native Go UI via `gioui.org`; no browser runtime or web frontend is required. Build the Windows executable with:

```powershell
go build -tags "desktop,production" -ldflags "-H windowsgui" -o dist\beacondesk-client-windows-amd64.exe .\cmd\client-windows
```

The UI defaults to Chinese and can switch between Chinese and English from Settings. Common actions stay on the main screen. Server address, transport mode, TLS options, device name, token, role, request mode, authorization toggles, trusted device revocation, audit-log review, update checking, simulated/screen-frame sending, and FPS/quality/resolution/bitrate presets live in a Settings panel with left-side navigation and right-side configuration panes. The home page does not show server details; they are shown and edited only in Settings.

Windows client settings are saved to `beacondesk-client.json` in the current working directory and are loaded automatically on startup. The `Start with Windows` option is off by default; when enabled by the user it writes a normal per-user `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` entry and can be turned off from Settings.

Settings also includes a Web Control page. The controlled user can choose a validity duration, generate a browser link, copy/open it, refresh active links, and revoke a selected link. Active links show their expiry. The link itself is not unattended authorization; every visitor session still appears as an incoming request and must be allowed locally.

The main view exposes target device ID/code, local temporary-code generation, incoming request approval, connection state, RTT, packet-loss estimate, bitrate, reconnect count, session mode, input permission state, and frame counters. After a session receives frames, the remote screen opens in a separate native window with JPEG preview rendering.

Trusted devices are stored locally in `trusted-devices.json`; audit entries are stored locally in `audit-log.json`. These files live under the current user's BeaconDesk config directory and should be protected by OS account permissions. UI settings live beside the executable/current command directory in `beacondesk-client.json`.

The Windows client can check the latest GitHub Release from `poouo/BeaconDesk`. It only displays version information and the release page link; it does not silently download, replace, or execute binaries.

## Server Install Script

After GitHub Releases are configured:

```bash
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- install
```

The installer downloads `SHA256SUMS` from the same release and verifies the selected server binary before installation. On first install it creates a WebSocket server with TLS enabled using a local self-signed certificate under `/etc/beacondesk/tls`; replace it with a trusted certificate for production and set `public_base_url` when serving through a domain.

One-line upgrade:

```bash
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- upgrade
```

Service commands:

```bash
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- start
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- stop
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- restart
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- status
```

Uninstall:

```bash
curl -fsSL https://raw.githubusercontent.com/poouo/BeaconDesk/main/scripts/install.sh | sudo sh -s -- uninstall
```

## Security Notes

- Remote control must require explicit target-side confirmation or preconfigured authorization.
- Temporary verification codes are short-lived, one-time server-side checks and do not replace target-side session approval.
- Mouse and keyboard injection is disabled by default and must be explicitly enabled on the controlled side.
- The server enforces the approved session mode; input messages are rejected unless the target approved input for that session.
- Local trusted-device reuse is visible, reversible from Settings, and not a hidden unattended-control mechanism.
- Web control links are temporary, revocable, and scoped to the generating controlled device. The server does not expose a public online-device directory.
- Local audit logs are intended for transparency and troubleshooting. They do not include screenshots or keystroke text capture beyond protocol metadata.
- Headless `-auto-accept` is for local testing and should not be used for unattended production deployment.
- Device secrets are stored in the local user configuration directory. Protect this directory with OS permissions and do not commit generated identity files.
- Server tokens in config files should be treated as sensitive secrets.
- Internet-facing deployments should use TLS, strong server tokens, firewall rules, monitoring, and regular release updates.
